# 城市社区适老化改造入户评估与施工交付平台

覆盖「**家属申请 → 社区核验/派单 → 评估师入户评估（平台五维度风险分级）→ 系统生成改造方案 → 家属增删确认（拒绝留痕）→ 社区补贴复核 → 施工队排期施工 → 现场变更（照片/材料/费用重算）回家属与社区节点 → 竣工验收 → 街道补贴审核 → 回写施工队结算 → 质保回访**」全流程的协同平台。

技术栈：**Vue 3 + Element Plus（Vite）｜ Spring Boot 3 + Spring Security + JPA/Flyway ｜ PostgreSQL 16 ｜ Docker Compose**

---

## 一、一键启动（宿主 docker compose）

```bash
cp .env.example .env          # 可按需改端口/密码，默认即可直接运行
docker compose up -d --build
```

- 浏览器访问：**http://localhost:3001**（端口取自 `.env` 的 `CC_PUBLISH_PORT`，验证环境已注入实际端口）
- 仅前端（nginx 非 root 运行于 8080）发布到宿主机；后端 8080、PostgreSQL 5432 **均不发布**，只在 compose 内网通信。
- 健康检查：前端容器 nginx 健康检查、后端 `GET /actuator/health`（由 Flyway 自动建表、应用启动时自动写入演示数据）。

停止与清理：

```bash
docker compose down           # 停止并移除容器（保留数据卷）
docker compose down -v        # 连同演示数据一起清除
```

## 三、推荐演示路径（一条工单走完全流程）

1. **家属** `zhangwei` 登录 →「提交改造申请」，填写楼层、独居、行动能力、跌倒史、卫生间/卧室现状、权属、电话、期望项目。
2. **社区** `wangli` → 待办工单 → 核验补贴资格（通过/不通过）→ 选择评估师派单。
3. **评估师** `lizhigu` → 录入门槛高度、卫生间尺寸、墙体材质、夜间照明、床边起身困难点、老人试行动作 → 提交。
   - 系统按评估结果自动生成方案：高门槛→坡道、蹲便→坐便改造、中高跌倒风险→L 形/一字扶手（安装工艺随墙体材质变化）、瓷砖湿滑→防滑处理、照明昏暗→感应夜灯、独居/高危→紧急呼叫按钮、起身困难→床边护栏。
4. **家属** → 查看每项的**改造原因、费用、补贴范围、施工影响**；可删除项目、新增项目（如厨房防撞）→ 签字确认。
5. **社区** → 家属增删后的方案重新出现待办，可逐项核定补贴上限（家属新增的非目录项目默认补贴 0），通过或退回。
6. **施工队** `chenjianguo` → 结合楼栋通行、电梯、材料到货、老人作息、邻里噪音限制排期 → 开工。
7. 施工中「提交现场变更」：墙体无法打孔 / 管线占位 / 老人临时住院 / 家属意见变化 / 材料型号不匹配 →
   **家属确认 → 社区复核**，通过后回到施工节点（任一环节驳回同样退回施工队）。
8. **施工队** 提交竣工验收：前后对比照片说明、老人试用记录、家属签字、材料与费用明细。
9. **街道** `sunjiwei` → 审核并核准补贴 → 系统自动生成**施工队结算单**（街道补贴拨付 + 家属自付 = 应付施工队）。
10. **施工队** → 结算后登记质保回访（满意/问题、下次回访日期），流程闭环。

## 四、入户评估风险分级

评估师入户时除采集门槛、尺寸、墙体外，还要现场记录**五个风险维度**，平台自动评分（满分 15）并生成等级，等级同步展示给社区工作人员与家属确认页：

| 维度 | 分值 | 判定要点 |
|---|---|---|
| 行动能力 | 0–4 | 独立 / 拄拐 / 需搀扶 / 轮椅 / 卧床 |
| 卫生间湿滑程度 | 0–3 | 干燥 / 一般 / 较湿 / 积水 |
| 床边起身难度 | 0–3 | 自如 / 略困难 / 明显困难 / 无法独立起身 |
| 夜间照明 | 0–2 | 充足 / 一般 / 昏暗 |
| 紧急呼叫条件 | 0–3 | 同住人、手机是否随身、离邻居距离、有无呼叫器 |

总分 **≥10 高风险、5–9 中风险、≤4 低风险**。平台同时生成主要风险因子说明。

- **高风险家庭**：自动要求施工队**优先排期**（待接单队列高风险置顶、列表标"优先"），接单时必须选择**家属全程陪同或临时照护/日间托管**并填写具体安排，否则不允许接单；页面展示评估师给出的施工安全照护建议。
- **家属拒绝高风险改造项目**（如紧急呼叫按钮）：删除时必须填写**拒绝原因**，系统同时保留**评估师建议说明**；该留痕出现在方案页，并在**街道补贴审核**时以"评估师说明 ↔ 家属拒绝原因"对照形式展示，可直接看到风险判断如何影响最终方案（演示工单 **#5 周福海**即高风险拒绝紧急呼叫的示例）。

## 五、施工变更与费用重算

施工队到场发现**墙体空鼓/无法打孔、瓷砖易裂、扶手位置被管线占用、材料型号不符、老人住院或临时要求增加项目**时，不能口头加价，必须在系统提报：

1. **上传现场照片**（档案编号/说明）、**变更说明**、**新材料需求**，并按明细行填写每个新增/替代项目的**材料费、人工费**（平台自动汇总，施工队无法手填总价）。
2. 变更先推**家属确认**；家属可驳回（维持原方案）。
3. 家属同意后交**社区工作人员判断是否影响补贴**，三选一：
   - **核准通过**：勾选哪些新增项计入可报销，通过后新增项目并入方案清单（标记"变更并入"），平台**重新生成项目清单、材料费、人工费、总费用和可报销金额**（受 5000 元总额封顶），并给出"本次新增可报销金额"；
   - **未通过**：保留原方案与原费用，变更费用不予认可；
   - **转社区协调**：工单进入"社区协调中"暂挂，协调期间不得按变更施工；协调后可采纳（费用自理）或维持原方案。
4. 未经流程通过的变更不进入清单、不影响竣工计价。演示工单 **#8 冯淑珍**（瓷砖易裂已核准重算）和 **#9 钱国栋**（墙体空鼓待家属确认）分别展示两种状态。

## 六、补贴规则（系统自动计算）

- 每个目录项目有「单项补贴上限」；方案补贴 = Σ(项目补贴上限 × 数量)，且受 **总额 5000 元封顶**、不超过工程总额双重约束。
- 家属**新增非目录项目**默认补贴为 0，必须经社区在复核环节重新核定后才可能纳入补贴——保证「家属增删 → 社区重新确认补贴规则」。
- 变更单核准后费用变化、街道最终核减，均在街道审核时以竣工总费用为准重算结算单。

## 七、工程结构

```
.
├── docker-compose.yml          # db(内网) + backend(内网) + web(唯一发布端口)
├── .env.example
├── backend/                    # Spring Boot 3 / Java 17
│   ├── Dockerfile              # 多阶段构建，非 root 运行 + HEALTHCHECK
│   └── src/main/
│       ├── resources/db/migration/V1__init.sql   # Flyway 建表
│       └── java/com/eldercare/
│           ├── domain/         # 12 个 JPA 实体
│           ├── repo/           # 数据访问
│           ├── service/        # WorkflowService 状态机、PlanGenerator 方案引擎、补贴计算
│           ├── security/       # JWT 登录鉴权（五角色）
│           ├── web/            # REST API
│           └── bootstrap/      # 演示账号与全节点演示工单
└── frontend/                   # Vue 3 + Vite + Element Plus
    ├── Dockerfile              # node 构建 → nginx 托管 + /api 反代
    ├── nginx.conf
    └── src/{pages,components}
```

## 八、本地开发（可选，非部署方式）

- 后端：`cd backend && mvn spring-boot:run`（需本机可访问 PostgreSQL，改 `application.yml` 中 `DB_HOST`）
- 前端：`cd frontend && npm install && npm run dev`（Vite 已把 `/api` 代理到 `localhost:8080`）

部署与验收以 **宿主 `docker compose up -d`** 为准。
